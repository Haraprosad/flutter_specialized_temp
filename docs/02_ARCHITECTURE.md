# Guide 2 — Architecture

Complete walkthrough of how this template is structured, what each file does, and how layers connect.

---

## Clean Architecture Overview

The template enforces strict **Clean Architecture** with three layers per feature. The dependency rule is simple: **outer layers depend on inner layers, never the reverse.**

```
┌─────────────────────────────────────────┐
│  Presentation (BLoC, Pages, Widgets)    │  ← Depends on Domain
├─────────────────────────────────────────┤
│  Domain (Entities, Use Cases, Repo IFs) │  ← Pure Dart, no dependencies
├─────────────────────────────────────────┤
│  Data (Models, DataSources, Repo Impls) │  ← Depends on Domain
└─────────────────────────────────────────┘
```

**Why this matters:**
- Domain layer has zero external dependencies — it's pure business logic
- You can swap the entire data layer (REST → GraphQL, local → remote) without touching presentation
- BLoCs depend on use cases (abstractions), not repositories (implementations)
- Every layer is independently testable

---

## SOLID Principles in This Codebase

| Principle | How It's Applied |
|---|---|
| **S** — Single Responsibility | Each class does one thing. A `UseCase` has one `call()` method. A `Repository` handles one domain concept. A `BLoC` manages one feature's state. |
| **O** — Open/Closed | New features don't modify existing code. Add a new feature folder, register it via `@injectable`, add a route. No core files change. |
| **L** — Liskov Substitution | Repository interfaces define contracts. `AuthRepositoryImpl` can be swapped with `AuthMockRepository` and the app works identically. |
| **I** — Interface Segregation | Repository interfaces are small and focused. `AuthRepository` has auth methods only. `TaskRepository` has task methods only. No god-interfaces. |
| **D** — Dependency Inversion | BLoCs depend on `LoginUseCase` (abstraction), not `AuthRepositoryImpl` (concrete). Repositories depend on `AuthRepository` interface, not `AuthRemoteDataSource` directly. Injectable resolves the graph. |

---

## Dependency Flow

```
UI (Page)
  └─→ BLoC (@injectable)
        └─→ UseCase (@injectable)
              └─→ Repository Interface (abstract class)
                    └─→ RepositoryImpl (@LazySingleton(as: Interface))
                          └─→ DataSource (@LazySingleton)
                                └─→ DioClient / AppDatabase
```

**Key rule:** Never call `sl<T>()` inside BLoCs, use cases, or repositories. Always use constructor injection.

### Entry Points & Flavors

## Layer Rules Summary

| Rule | Why |
|---|---|
| Domain layer imports nothing from `data/` or `presentation/` | Keeps business logic framework-free and testable |
| BLoCs import use cases, not repositories | Single Responsibility — BLoC manages state, use case contains business logic |
| Use cases import repository interfaces, not implementations | Dependency Inversion — swap implementations without changing use cases |
| Repository impls import datasources, not the other way | Data flow is one-directional |
| Models have `toEntity()` to convert to domain | Only domain types cross the domain/data boundary |
| All DI is constructor injection via Injectable | No hidden dependencies, fully testable |
| Error handling uses `AppException` in BLoCs, not `DioException` | Error types shouldn't leak across layers |
